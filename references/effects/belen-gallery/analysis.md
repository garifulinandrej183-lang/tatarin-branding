# Технический анализ интерактивной галереи Belen Jones

Механика исходника и инструкция для Codex

Главный эффект — пространственная галерея из четырёх плоскостей, которые поворачиваются вокруг оси X. Источник использует прямой Three.js, видеотекстуры и GSAP. Desktop и mobile имеют разные модели управления и движения.

Документ отделяет наблюдения браузера, выводы по опубликованному коду и требования к независимой адаптации. Полный раздел «Инструкция для Codex» можно использовать как техническое задание; отдельный TXT предназначен для копирования.

## 1 Статус исследования и границы достоверности

Источник: https://www.belenjones.com/. Проверка: 5 октября 2026 года, облачный Chrome, скриншот viewport 1180 × 757.

Главный объект анализа — интерактивная проектная галерея главной страницы: переключение проектов, пространственная композиция, управление и раскрытие проекта. Контактный блок, оформление текстов и индивидуальные страницы проектов рассматриваются только в той мере, в какой участвуют в этой механике.

В этом сеансе визуальный тест анимации не состоялся. Сразу после исходной загрузки документ сменился экраном «Application error: a client-side exception has occurred». Console log указывает: THREE.WebGLRenderer: A WebGL context could not be created, GL_VENDOR = Disabled, GL_RENDERER = Disabled, затем Error creating WebGL context. Одна перезагрузка не восстановила страницу. Это конкретное ограничение WebGL в исследовательском браузере, а не доказательство, что сайт не работает у обычных посетителей.

Поэтому ниже необходимо различать:

- Наблюдение: действительно прочитанный DOM, консоль или полученный скриншот.

- Код: механика, установленная из публичного клиентского кода; это не покадровая визуальная проверка.

- Рекомендация: выбранный способ воспроизвести принцип в другом проекте; не утверждение о точном устройстве оригинала.

Не проверены в живом движении: итоговый рисунок перспективы, кадрирование переходов, реальные времена до стабилизации, cursor-follow, touch-жесты, поведение при ресайзе и reduced motion оригинала. Мобильный viewport не эмулировался: в документированном интерфейсе браузера нет команды изменения viewport, а падение приложения делает такую проверку бессмысленной.

## 4 Механика опубликованного кода

Это не обычная плоская горизонтальная карусель и не вращение вокруг вертикальной оси. Четыре прямоугольные плоскости расположены спереди, сверху, сзади и снизу. Внутренняя группа поворачивается вокруг X, раскрывая следующий проект четвертью оборота. Внешняя группа уже имеет наклон и разворот, поэтому вращение читается объёмно, под углом к зрителю.

Подтверждённые параметры главного renderer:

- PlaneGeometry desktop: 6.4 × 4 мировых единицы; mobile: 3.5 × 6. Глубина объёма равна высоте плоскости. Это четырёхгранный «барабан» с прямоугольным фронтом, а не обязательно геометрический куб.

- Внутренний поворот: rotation.x = step · π/2.

- Desktop parent: rotation.y = −π/6 (−30°), rotation.x = 0.25 rad (≈14.3°); uniform scale = 1.5555556; position.z = −5, position.y = −0.5.

- Перспективная камера: FOV 45°, desktop position = (0, 2.5, 9), mobile = (0, 0, 9).

- Один дискретный переход: 0.9 s, GSAP power2.inOut. Прыжок на несколько пунктов: min(0.9 + (jump−1)·0.25, 2.5) s.

- Видео нанесены как VideoTexture на MeshBasicMaterial. Сложный пользовательский shader для самого основного эффекта не требуется.

- Mobile меняет ход анимации: для локальной доли scroll progress f сначала 0–0.5 удержание; 0.5–0.6 уменьшение масштаба 1→0.5; 0.6–0.9 поворот на четверть; 0.9–1 увеличение 0.5→1.

Параллакс здесь прежде всего возникает из настоящей перспективной проекции и пространственного вращения плоскостей. Не следует автоматически объяснять эту глубину cursor-follow или несколькими слоями CSS: таких выводов из неподвижного кадра делать нельзя.

### Последовательность состояний оригинала

1. Desktop вступление: внешняя группа V перемещается x=19→0 и вращается вокруг Z от −2π до 0 за 2.2 s, power2.inOut. Это отдельный вступительный жест, не поведение при каждом wheel.

2. Покой: наклонённая группа H показывает фронтальную работу; DOM-навигация и сведения синхронизированы с индексом.

3. Перелистывание: wheel со знаком направления меняет целочисленный step; внутренний k поворачивается на 90° по X за .9 s. После завершения ещё 350 ms блокируются новые команды. Смена текстур переиспользуемых граней выполняется посередине перехода. Активное видео играет, остальные paused.

4. Наведение: raycast невидимого box-hit-area меняет курсор и подсказку. Изменения rotation, deformation или постоянного camera-follow при обычном hover в компоненте не найдено.

5. Открытие: click по hit-area запускает WebGL zoom H: за .65 s с power3.inOut rotation→(−.278,0,0), scale→coverScale, y→baseY−.6. После этого появляется отдельный DOM overlay проекта; время видео передаётся ему с компенсацией +.6 s. Это не буквальное превращение mesh в HTML.

6. Закрытие: за .5 s power2.inOut восстанавливаются исходные scale/rotation/y; DOM overlay очищается через 500 ms.

7. Next внутри раскрытого desktop-проекта: shrink .35 s, затем поворот .9 s, затем grow .35 s с перекрывающимися участками. Это отдельный сценарий; его нельзя заменить обычным wheel при открытом detail.

### Ввод фон и вторичные эффекты

Desktop input. Реальный порог wheel в коде всего |deltaY|≥5; дальше шаг ±1, не пропорциональное углу отслеживание скорости wheel. В desktop touch-ветке порог 30 px. Отрицательный step блокируется при step≤0. Названия проектов вычисляются modulo 9, но геометрических поверхностей четыре. Клик по пункту списка может дать многопунктовый jump с более длинной длительностью. PageContainer занимает 100vw×100vh, overflow:hidden и touch-action:none.

Mobile input. JS mobile определяется как innerWidth<768, CSS использует max-width:768px: на точной границе есть различие. На мобильном документ прокручивается нативно, canvas fixed. Spacer для девяти работ — 1450vh. При i=scrollY/innerHeight: intro=clamp(i,0,1), progress=max(0,(i−1)/1.5)+offset; около целых progress применяется snapping в пределах .05. Один проект занимает 1.5 высоты viewport, до этого один viewport занят intro. Mobile H.rotation=(0,0,0), итоговый scale=coverScale·phaseScale·(.5+.5·intro). После окончания intro код удерживает нижнюю границу scrollY у одной высоты viewport при попытке вернуться выше. Открытие детали на mobile идёт через отдельный заголовок, desktop raycast interactions там отключены. Mobile heading скрывается в основной фазе поворота: видим при fraction<.5 или ≥.85. Эти ветки прочитаны в коде, не проверены пальцем на устройстве.

Кадрирование. Видео использует centered cover через texture.repeat и texture.offset; desktop учитывает параметр cubePullback. Это UV crop, не clip-path и не custom shader. Материал double-sided; невидимый BoxGeometry применяется лишь как hit-area. Картинки/видео не выступают за прямоугольные planes. В ходе вращения перспектива и взаимное перекрытие граней дают глубину; дополнительного postprocessing для неё не требуется.

Фон. Desktop — отдельная DOM-полоса из 50 цветных секций по 100vh. На шаге s transform.y=−(25+s)·innerHeight, transition через GSAP .9 s power2.inOut. Внутри blur 80 px, opacity .55, базовый цвет #f5f4f2. Mobile вместо полосы меняет fixed background-color за .6 s. Это CSS-слой, не WebGL blur. Количество фоновых секций конечно, поэтому бесконечное продвижение потенциально исчерпывает полосу; это гипотеза дефекта по коду, не воспроизведённая ошибка.

Дополнительный физический режим. Hold Space включает gravity-driven drag; pointerdown по hit-area создаёт constraint к кинематической точке, pointermove её двигает. Gravity=(0,−18,0), границы x±3.5; rebound .45; linearDamping .3, angularDamping .25. Отпускание Space возвращает позу за .7 s power2.out. Это вторичный режим взаимодействия, не обязательная часть основного scroll-эффекта. В проверяемой адаптации его лучше добавлять после устойчивой основной галереи. Название конкретного physics-пакета не установлено надёжно.

Типографика и сведения. Навигация — DOM-слой с контурными неактивными буквами и заполнением активных; часть текста использует mix-blend-mode:difference. Эти детали влияют на арт-дирекцию, но не создают основную пространственную механику.

### Формула coverScale и назначение граней

В оригинале q=tan(22.5°), A=viewportWidth/viewportHeight, w и h — размеры plane:

coverScale = 1.08 · max(28q/(h+hq), 28qA/(w+hqA)).

Это масштаб под конкретную камеру/композицию, а не универсальная формула для любой сцены. При смене FOV, расстояния или положения камеры пересчитать покрытие, а не слепо сохранить коэффициент 28.

Для physical face f и step s исходный код назначает проект так:

projectIndex = positiveModulo(f + 4·max(0, floor((s−f+1)/4)), projectCount).

Проверить отдельно шаг назад, переход через последнюю работу, jump по меню и смену media map в середине поворота. Не рассчитывать, что четыре заранее назначенных материала позволят показать все девять работ без переиспользования.

### Доказательная основа параметров

- A  Обработчики страницы, CSS и мобильный progress

- B  Главный renderer, геометрия, камеры, zoom и physics

- C  Данные проектов и привязка динамического renderer

- D  GSAP bundle

React, Next.js, прямой Three.js и GSAP подтверждены. Официальный GSAP-пост отмечает ScrollTrigger, однако рассмотренные wheel/mobile-ветки устроены через собственные обработчики и GSAP; не следует из этого делать вывод, что сам поворот обязательно управляется ScrollTrigger. Не подтверждены Lenis, React Three Fiber или пользовательская GLSL-деформация главного эффекта.

## 5 Дополнительные параметры кода

Следующие уточнения относятся к опубликованным модулям страницы и renderer. Они дополняют разбор выше и не являются результатом визуального тестирования.

### Связь модулей и устройство renderer

Модуль страницы A содержит dynamic import e.A(6072), loadableGenerated.modules=[5135], ssr:false. Модуль данных C связывает 6072 с chunk B и module 5135; B переэкспортирует module 216, где расположен renderer. Страница передаёт step, isMobile, disabled, onSettled и callbacks zoom. Это связь конкретного компонента с главной страницей, а не вывод из наличия библиотеки в сборке.

Размер прочитанного chunk B — 615775 байт. Начало компонента: var lG=e.i(4199);let lW=-Math.PI/6. PerspectiveCamera задаётся параметрами (45, width/height, 0.1, 100), направлена lookAt(0,0,0). WebGLRenderer создаётся с antialias:true и alpha:true; pixelRatio=min(devicePixelRatio,2). Рендер вызывается через gsap.ticker.add(ey), затем renderer.render(scene,camera).

Иерархия групп: V → H → k. V отвечает за вступление, H за общую позу и zoom, k за прокрутку граней. H.rotation.z=0; базовый scale в исходнике записан как 1.5555555555555556. Mobile position.y=0. Mobile playEntry сразу вызывает callback, без desktop вступления.

Каждая грань — PlaneGeometry(width,height) и MeshBasicMaterial с side=2, то есть двусторонний материал. Невидимый hit-area — отдельный BoxGeometry(width,height,height) с opacity=0. Он не создаёт непрозрачные боковые стены.

Точные позиции и углы граней относительно k при h=faceHeight:

front: position=(0,0,h/2), rotation=(0,0,0)

top: position=(0,h/2,0), rotation=(−π/2,0,0)

back: position=(0,0,−h/2), rotation=(π,0,0)

bottom: position=(0,−h/2,0), rotation=(π/2,0,0)

Custom ShaderMaterial, postprocessing, displacement и GLSL-маска главного эффекта в этом компоненте не найдены. Shader strings движка Three.js сами по себе их не доказывают. Упоминания custom GLSL в описаниях портфолио относятся к клиентским проектам.

### Текстуры и готовность медиа

Видео создаются как HTMLVideoElement с loop, muted, playsInline, preload=auto и crossOrigin=anonymous, затем оборачиваются в VideoTexture. Изображения загружаются через TextureLoader. Цветовое пространство — sRGB; video filters=1006, то есть LinearFilter. Для изображений применяется максимальная поддерживаемая renderer anisotropy.

На mobile при наличии выбирается landingMobile; иначе mainVideo либо mainCubeImage/landingImage. Оригинал использует отдельные мобильные assets там, где они предусмотрены. Desktop pullback=cubePullback??1, mobile pullback=1.

Centered cover crop задаётся для mediaAspect=m, faceAspect=f и pullback=p:

если m > f: repeat=(f/m*p, p)

иначе: repeat=(p, m/f*p)

offset=((1-repeat.x)/2, (1-repeat.y)/2)

В исходных данных девять проектов: SENSE, ASAP Rocky, Bvlgari, GANT, Trident, Not in Miami, Gemini, Ksawery, Panda Express. Эти имена приведены только для проверки количества и сопоставления с источником. В новой реализации использовать собственные названия и материалы.

Четыре поверхности переиспользуются; изменившиеся map на desktop заменяются в момент 0.5*duration. Активное видео запускается, остальные ставятся на паузу. Готовность определяется гонкой загрузки менеджера и первого видео с timeout 3000 ms. playActive повторяет попытку каждые 300 ms до 3 s; unlockAll при необходимости запускает и останавливает остальные видео. Catch отказа autoplay пустой. Loader не гарантирует готовность всех видео.

### Точные детали переходов и оформления

Desktop wheel вызывает preventDefault; игнорирует |deltaY|<5 и заблокирован при анимации или overlay. Соседний wheel cycle занимает ориентировочно 0.9+0.35=1.25 s по таймингам кода, без учёта других состояний. Навигация задаёт выбранный step; номера и подписи вычисляются modulo 9. Верхняя граница положительного wheel step в обработчике не задана.

При zoom sidebar уходит вверх на высоту viewport за 0.45 s, power2.in. В callback передаются index и currentTime активного видео; overlay получает currentTime+0.6 s. ExitZoom занимает 0.5 s; closing flag и очистка overlay привязаны к 500 ms.

Desktop Next внутри zoom: shrink до 1.5556 за 0.35 s с power2.in; поворот k на следующие 90° за 0.9 s с offset 0.25; grow до coverScale за 0.35 s с power2.out и overlap 0.2 s; texture swap на 0.7 s. Mobile Next в overlay использует progress tween 1.25 s с power2.inOut после задержки 120 ms.

Mobile current index=floor(progress+0.25). Spacer 1450vh — высота spacer для девяти проектов, не максимальный scrollY. Все mobile pointer interactions renderer отключены через disabled=true; проект открывает отдельный heading.

CSS идентификаторы слоёв: landing__BgStrip, BgStripSection, BgStripBlur, MobileBg, CubeWrapper. Начальная позиция desktop полосы −25*innerHeight. У размытого слоя inset=−80px, filter=blur(80px), opacity=0.55; специальная ветка @supports для Safari снимает filter. Mobile BgStrip скрыт, fixed фон имеет opacity=0.55. DOM-навигация в источнике использует Monument Extended Ultrabold; неактивный текст получает -webkit-text-stroke:1px, активный — белую заливку. Это описание исходника, не требование копировать его шрифт или оформление.

### Физика и непроверенные риски

Физический world действительно подключён, но имя и версия пакета по bundle надёжно не установлены. Помимо gravity=(0,−18,0), rebound=0.45, linearDamping=0.3 и angularDamping=0.25, contact material задаёт friction=0.6 и restitution=0.08. Тикер выполняет step(1/60,min(delta,0.05),3). Space доступен на desktop, когда disabled=false; pointerdown создаёт point constraint к kinematic point.

В компоненте WebGLRenderer создаётся напрямую, альтернативная CSS или 2D версия в рассмотренном коде не найдена. Различие CSS max-width:768px и JS innerWidth<768 существует в точке 768 px. Конечные 50 фоновых секций при неограниченных положительных шагах создают риск исчерпания фона, который не воспроизведён.

В ветке step-effect при N.current, связанной с physics, встречается y:cubeY; имя cubeY найдено во всём chunk B только один раз, другие пути используют G. Это вероятный ReferenceError при определённом сочетании physics и step, а не подтверждённый live баг. Не приписывать оригиналу spring easing, зависимость деформации от wheel speed, Lenis, React Three Fiber или shader mask без дополнительных доказательств.

## 6 Принципы независимой адаптации

Переносить следует связь «ввод → смена пространственного состояния → согласованная смена текста → раскрытие работы». Не нужно переносить имена, фотографии, видео, шрифтовой рисунок, фирменные тексты или композицию пиксель в пиксель. У новой реализации должны быть свои данные и свои лицензированные материалы.

Ключевые качества реализации:

- Переход воспринимается как одно связное перемещение сцены, а не независимые случайные эффекты.

- Активный проект однозначен; название, описание, счётчик и действие открытия относятся к нему же.

- Скролл/жест не запускает конфликтующие анимации.

- Открытие работы отделено от команды перелистывания.

- Геометрия и медиа стабильны: нет прыжков после загрузки, неверных пропорций или пустых кадров.

Декоративные качества, которые можно менять без потери принципа: гарнитура, палитра, размеры полей, оформление курсора, детали индикаторов, текст вступления, часы и город. Параллакс и микроанимации также не должны скрывать основной переход.

## 7 Инструкция для Codex

Ниже — самодостаточное задание для независимой реализации. Числа этого раздела, если не сопоставлены выше с клиентским кодом источника, являются проектными стартовыми значениями, а не результатами замера Belen Jones.

### Задача и ограничения

Сделай интерактивную проектную галерею с пространственным переключением граней и согласованным DOM-интерфейсом. Используй существующий стек проекта; сначала прочитай его инструкции и структуру. Если проекта нет, подготовь минимальную React/TypeScript-реализацию с Three.js и GSAP. Не устанавливай одновременно несколько анимационных систем. Не копируй контент, бренд и медиа Belen Jones; создай нейтральные демонстрационные данные. Не публикуй и не меняй внешние сайты.

Результат должен содержать рабочую страницу, отдельный конфиг движения, читаемую модель состояний, CSS для desktop/mobile/reduced-motion, fallback без WebGL и короткий README с запуском и проверками.

### Модель данных и слои

Project = {id, title, summary, role, tags, image, video?, href?, accent}. ID стабилен и не зависит от физической грани.

1. Layout-слой: размер сцены, безопасные поля, DOM-навигация, текст, кнопки.

2. Scene-слой: камера, группа граней, материалы и соответствие logical project → physical face.

3. Motion-слой: один владелец transform каждого объекта; таймлайн перехода, параллакс, раскрытие.

4. Input-слой: wheel, pointer, keyboard, touch; всё преобразуется в команды next/prev/open/close, не пишет transforms напрямую.

5. Resource-слой: статичные превью, ленивое видео, cleanup, обработка отказа.

Не добавляй опциональный Space+physics drag в первую версию: это вторичный эффект. Предусмотри отдельный флаг для него; основная галерея должна быть закончена без физического движка.

Не рендери обычный текст в WebGL только ради эффекта. Сохрани доступные заголовки, ссылки и кнопки в DOM. Canvas декоративный относительно DOM-структуры.

### Модель состояний

- BOOT: загрузить только минимальные ресурсы текущей и соседних работ; интерфейс не ждёт все видео.

- IDLE(index): активная работа, доступны next/prev/open.

- TURNING(from, to, direction): единый переход к соседнему проекту. Повторный wheel внутри того же жеста игнорировать; допустимо запомнить максимум одну следующую явную команду.

- OPENING(index): перелистывание заблокировано, текущая работа раскрывается.

- DETAIL(index): обычная прокрутка контента проекта, действия prev/next не перехватывают её.

- CLOSING(index): возврат к тому же выбранному проекту и положению фокуса.

- FALLBACK: доступный статичный список/слайдер, если WebGL не поддерживается, потерян контекст или загрузка сцены завершилась ошибкой.

Событие resize не должно сбрасывать index. Смена breakpoint должна отменять текущую анимацию, вычислять корректное конечное состояние, освобождать старые слушатели и переинициализировать только сценический режим. Escape закрывает detail, после закрытия фокус возвращается на кнопку открытия. Кнопки prev/next и клавиатура обеспечивают полный альтернативный путь без мыши.

### Геометрия и движение

Обозначения: OuterGroup соответствует группе H, innerGroup — группе k исходника. В формулах логический шаг k является числом; в коде назови его step, чтобы не путать с объектом группы. V — дополнительная внешняя группа для вступления.

Создай четыре плоскости вокруг X-оси, расположенные front/top/back/bottom. Задай их явно: front position(0,0,h/2), rotation.x=0; top position(0,h/2,0), rotation.x=−π/2; back position(0,0,−h/2), rotation.x=π; bottom position(0,−h/2,0), rotation.x=π/2. Проверь направление нормалей и ориентацию видео на каждой плоскости: верх/низ не должны случайно показывать перевёрнутый материал после поворота. Используй PlaneGeometry, не обязателен BoxGeometry. Нельзя создавать девять геометрических граней только потому, что в списке девять проектов: переиспользуй четыре физических слота.

Для логического шага k целевой поворот innerGroup.rotation.x = k·π/2. OuterGroup хранит общий наклон и положение. Поскольку k может возрастать, не нормализуй угол посреди таймлайна. После завершения безопасно нормализовать его на кратное 2π, сохранив отображение индексов. Для перехода назад используй корректный positiveModulo: ((n % count) + count) % count.

Пусть u = clamp((time - start)/duration, 0, 1). Для соответствия найденному коду используй GSAP power2.inOut и duration = 0.9 s на один шаг; theta(u) = mix(theta0, theta1, easing(u)). Для прыжка на jump шагов duration = min(0.9+(jump−1)·0.25, 2.5). Не добавляй второй сглаживающий фильтр поверх таймлайна.

Не добавляй на desktop незапрошенное уменьшение в середине обычного поворота, подпрыгивание, пружину или завал всех осей. Mobile shrink — отдельная подтверждённая механика, не повод переносить её на desktop.

Используй перспективную камеру. Для близкой механики начни с FOV 45°, camera (0,2.5,9), OuterGroup position (0,−0.5,−5), rotation (0.25,−π/6,0), scale 1.5555556, face 6.4×4. Это исходные параметры, не адаптивный закон для всех viewport. При необходимости подбери distance аналитически: distance = visibleHeight/(2·tan(fovY/2)), учитывая aspect ratio и максимальную глубину вращающейся фигуры. Сначала обеспечь правильный размер фронтальной грани и отсутствие обрезания в середине оборота, затем подбирай перспективу. Не меняй одновременно fov и distance на каждом кадре.

### Скролл и курсор

В точной базовой механике: |deltaY|≥5 запускает ±1 step, input lock держится до onSettled + 350 ms. Это можно воспроизвести напрямую. Для более устойчивой адаптации к разным трекпадам применяй следующий улучшенный вариант: на desktop одна законченная команда wheel должна означать один переход, а не один поворот на каждое событие браузера. Нормализуй deltaMode в пиксели, накапливай deltaY, используй порог примерно 45 px и dead zone. Сброс накопления после паузы около 140 ms; запрети повторный триггер инерционного хвоста до завершения перехода и нового жеста. Значения должны быть вынесены в конфиг. Перехват допустим только внутри интерактивной галереи, никогда внутри detail и скроллируемых панелей.

В оригинальном hover такой параллакс не обнаружен. Для близкого воспроизведения оставь его выключенным. Если арт-дирекция новой работы отдельно требует pointer-параллакс, это отдельный необязательный слой, не источник переключения. Нормализуй pointer относительно контейнера: nx = 2·(x-left)/width-1, ny = 2·(y-top)/height-1. Рекомендуемый предел yaw ±2°, pitch ±1.5°. Сглаживание, независимое от частоты: a = 1 - exp(-dt/tau), current += (target-current)·a, tau ≈ 0.12 s. На pointerleave плавно верни target к нулю. Если референс требует фиксированной камеры, оставь коэффициенты нулевыми. Отключи на coarse pointer и reduced-motion.

Click не должен открывать проект после drag. Запоминай pointerdown, считай смещение; при превышении 8 px отменяй click/open. DOM-кнопки работают независимо от raycast. Кастомный курсор никогда не должен быть единственным носителем подсказки; на touch он отсутствует.

### Кадрирование маски и раскрытие

Для заданных выше camera/geometry вычисляй q=tan(22.5°), A=viewportWidth/viewportHeight, w=faceWidth, h=faceHeight; coverScale=1.08·max(28q/(h+hq),28qA/(w+hqA)). Эта формула привязана к данной камере; после её изменения пересчитай покрытие по проекции.

Медиа заполняет грань по правилу cover без растяжения. Для frameAspect f = frameWidth/frameHeight и mediaAspect m = mediaWidth/mediaHeight: если m > f, samplingWidth = f/m и samplingHeight = 1; иначе samplingWidth = 1 и samplingHeight = m/f. UV центрируй и умножай на эти коэффициенты. Для DOM-постера используй object-fit: cover.

Граница самого viewport — обычный overflow: hidden. Граница прямоугольной плоскости — её геометрия/UV; shader mask нужна только при реальном эффекте нестандартного reveal, не по умолчанию. Следи за near/far camera clipping и backface visibility. Не путай исчезновение оборотной стороны с CSS clip-path.

Для соответствия источнику сначала анимируй H за .65 s power3.inOut к rotation(−.278,0,0), scale=coverScale, y=baseY−.6; после этого открой отдельный DOM overlay. При закрытии возвращай H за .5 s power2.inOut. Синхронизируй время видео; не представляй этот переход как mesh→HTML morph. Упрощённая альтернатива, если WebGL-раскрытие не нужно: fade сцены и DOM-панели за .55 s. Не вводи FLIP/morph mesh→HTML без отдельного требования. Не анимируй layout/измерения в каждом rAF. Close должен быть обратимым при resize и медленной загрузке видео.

### Mobile доступность и reduced motion

Мобильный режим должен быть самостоятельным. Для близкого воспроизведения используй нативную вертикальную прокрутку как источник progress и отдельную композицию: face 3.5×6, camera (0,0,9). H.rotation=(0,0,0), position=(0,0,−5); intro=clamp(scrollY/viewportHeight,0,1); progress=max(0,(scrollY/viewportHeight−1)/1.5), если программная навигация не добавляет offset. Высота spacer=(1.5·projectCount+1)·viewportHeight; canvas fixed. Итоговый H.scale=coverScale·scale(f)·(.5+.5·intro). Не переносить desktop wheel-lock на touchscreen.

Для каждого шага отдели целую часть k = floor(progress) и долю f = progress−k.

Определи scale(f): 1 при f<0.5; mix(1,0.5,(f−0.5)/0.1) при 0.5≤f<0.6; 0.5 при 0.6≤f<0.9; mix(0.5,1,(f−0.9)/0.1) при f≥0.9.

Определи turn(f)=0 при f<0.6; (f−0.6)/0.3 при 0.6≤f<0.9; 1 далее.

rotation.x=(k+turn(f))·π/2.

Это передаёт кодово подтверждённую структуру hold → shrink → turn → grow; указанные кусочно-линейные зависимости повторяют функцию setMobileProgress. Не добавляй произвольные easing на каждый участок, если это ломает привязку к обратному скроллу.

Упрощённая адаптация для слабых устройств: нативная вертикальная лента статичных карточек с устойчивым aspect ratio. Название и действие открытия видимы постоянно; весь контент доступен без WebGL.

Прими единый breakpoint 768 px в CSS и JS, устранив различие <768 и ≤768 исходника; затем проверь реальные ограничения текста и медиа. Используй 100svh/dvh осознанно, учитывай safe-area и изменение браузерной панели, не рассчитывай высоту только по старому innerHeight.

При prefers-reduced-motion показывай активную работу без пространственного поворота/параллакса. Смена мгновенная либо fade 0.12–0.18 s; все кнопки и контент остаются. Системная настройка должна отслеживаться и при изменении во время сеанса. Не делай reduced-motion пустым или менее функциональным режимом.

### Производительность и устойчивость

- Один requestAnimationFrame/render loop. GSAP и ручной lerp не управляют одной величиной одновременно.

- DPR ограничить до min(devicePixelRatio, 1.5–2); на слабых мобильных устройствах можно ниже.

- Не держать запущенными все видео: текущее играет, соседнее предзагружено, остальные paused. playsInline/muted; отклонение autoplay обрабатывать постером.

- Пауза при document.hidden и вне viewport; освободить texture/material/geometry/video/listeners при unmount.

- Не вызывать React setState каждый кадр. Движение в refs/scene objects; DOM-статус менять на дискретных переходах.

- Текстуры ограничить разумным разрешением; задать размеры до загрузки. Ошибка одного файла не ломает всю сцену.

- При webglcontextlost перейти в fallback или восстановить состояние без потери контента. Не повторять наблюдавшийся у источника белый экран.

### Критерии приёмки

1. Один wheel-жест даёт один логический переход; длинный инерционный хвост не прокручивает несколько работ.

2. Быстрые повторные next/prev не рассинхронизируют грань, заголовок, метаданные и кнопку.

3. Цикл проходит число проектов, отличное от четырёх; переход последняя → первая и обратный корректны.

4. При раскрытии, закрытии, resize и смене ориентации сохраняется выбранная работа; нет внезапного прыжка к первой.

5. Проверены 1440×900, 1024×768, 390×844 и 360×800, отдельно keyboard, touch и reduced-motion. Не заявлять проверенные размеры без фактического теста.

6. Контент остаётся доступен без WebGL, при ошибке текстуры и при запрещённом autoplay.

7. Desktop сцена укладывается в бюджет около 16.7 ms/frame на целевом тестовом устройстве; сообщить устройство и реальные измерения, а не обещать универсальные 60 fps.

8. В проекте не скопированы авторские медиа, тексты, названия, логотипы и фирменное оформление источника.

9. README разделяет реализованные, проверенные и оставшиеся ограничения. Итог приложить с последовательными скриншотами рабочих состояний и короткой записью движения, если среда поддерживает её.
