# Порядок использования в Codex

1. Прочитать AGENTS.md целевого проекта, package.json/lockfile, состояние git и его дизайн-правила. Существующий стек и явные инструкции пользователя имеют приоритет.
2. Открыть references/CATALOG.md или catalog.json, выбрать один ID. Если указаны слова «как спираль», выбрать pacome-spiral; «кольца и символы» — alphabet-symbols; «пролёт через маску» — podium-scroll; «цветная жидкость» — helloshivam-fluid; «мозаика портрета» — quartr-portrait; «поворот барабана» — belen-gallery.
3. Прочитать выбранные README, analysis, codex-prompt, implementation и VALIDATION. Не считать старый prompt командой переписать новый сайт; адаптировать его к текущей задаче. Старые «не публиковать» и остальные ограничения относятся к прежнему заданию, текущий пользователь определяет публикацию.
4. Прочитать перечисленные исходники. Portable JS подходит vanilla проекту; React/TS snapshot — источник для React интеграции. Выбрать один renderer/loop, не загружать оба одновременно. Сохранённый контент заменить фактическими данными текущего сайта.
5. Составить краткий mapping: контейнер → ввод → состояния → координаты/маска → renderer → lifecycle. Сначала реализовать ключевую механику. Меню, typing, цвета, фото и фирменные формы добавлять лишь если это требуется новым заданием.
6. Если WebGL недоступен, использовать описанный fallback. Падение облачного WebGL не доказывает ошибку модели или референса. Для визуального сравнения получить запись/покадровые снимки локально в браузере с GPU; исходники и статичные кадры не подтверждают FPS, инерцию и touch. Открывать исходный сайт повторно только когда это требуется для отсутствующего факта или нового визуального сравнения.
7. Проверить реальные сценарии: первый вход, 20 s покоя, курсор, быстрый/медленный ввод, обратный scroll, drag vs click, pointercancel, resize/orientation, pause, hidden tab, reduced motion, отсутствие WebGL, клавиатура, работоспособность ссылок. Проверить целевые desktop/mobile размеры и сообщить, какие проверки фактически выполнены.
8. Сохранить в целевом проекте docs/effect-implementation.md: выбранный ID и commit архива, исходный source commit, изменённые файлы, зависимости, настройка параметров, проверенные сценарии, ограничения. Не менять этот каталог и не публиковать материалы от имени пользователя без соответствующего задания.

## Дизайн

Применять [UI_GUIDELINES](../docs/UI_GUIDELINES.md) и [официальную подпись](../docs/USAGE.md) сообразно задаче. Подпись — локальный официальный asset; typing надписи не заменяет правила брендинга. Не добавлять статистику, лишние панели и контент ради демонстрации эффекта. Сохранить SEO, формы, текущие маршруты и основные действия.

## Доверие к сведениям

analysis.md — прежний разбор; implementation.md — собственное применение; SOURCE_MANIFEST.json — происхождение и SHA-256 кода; VALIDATION.md — конкретные прогоны. Предложенные параметры не выдавать за измерения оригинала. Для analysis-only сначала создать и проверить свою адаптацию. Не копировать чужие bundles, графику, видео, логотипы или тексты из референса. Сохранять внешние license notices применённых алгоритмов.
